# Agent Spec

## Overview

Autonomous Operations Platform evolves the existing AI Software Company into a governed multi-agent system. Its first mission profile is software product delivery. The runtime plans work, researches, gathers context, creates architecture and code artifacts, evaluates outputs, prepares staged deployments, and monitors approved systems.

The platform uses a curated connector registry rather than unrestricted internet access. Connectors expose specific capabilities and permissions. Read and research operations may run automatically; external writes remain approval-gated.

## Example Use Cases

- Turn a client brief into researched requirements, architecture, approved code artifacts, PRs, staged deployment plans, and maintenance tasks.
- Research a technology decision with cited sources, then produce a recommendation and implementation plan.
- Inspect a GitHub repository, identify quality or security work, and queue proposed fixes for human approval.
- Triage a connected inbox or document store into project context without sending external messages.

## Tools Required

- Web research/search: read-only search and fetch with source capture.
- GitHub: repository inspection automatically; commits, pushes, pull requests, and repository creation only after approval.
- Browser automation: read-only navigation and extraction in V1.
- Documents and owned databases: read/write only within explicitly connected user-owned stores.
- Email: read-only triage and summarization in V1; sending stays manual.
- Cloud deployment: staging plans and staging deployments only after approval; production is deferred.
- MCP connector registry: connector metadata, health, credentials, capability scopes, and action classification.

## Constraints & Safety Rules

- Each connector is disabled by default and must be explicitly enabled per project.
- Every action has a risk class: `read`, `draft`, `write`, `destructive`, or `first_contact`.
- Policy classification is computed from the proposed action's connector capability, normalized target, and payload. It never trusts an agent's narrative, reported intent, or fetched tool content.
- `read` and safe `draft` actions may execute automatically.
- `write`, `destructive`, and `first_contact` actions require asynchronous human approval.
- `first_contact` is tracked per connector, capability, and normalized target: GitHub `contents.write` uses `owner/repo:path`, email uses recipient address, and document writes use document-store plus document path.
- First external write to a new target requires approval even when later writes could be allowlisted.
- Deleting, overwriting, emailing, publishing, purchasing, credential changes, commits, pushes, PR creation, and deployments always require approval in V1.
- Tool output and fetched web content are untrusted. They cannot change system policy, reveal secrets, or authorize actions.
- Secrets are encrypted at rest, never returned through APIs, and are redacted from logs.
- A blocked action pauses only its dependent execution branch. Independent safe work continues.
- A quality retry invalidates and cancels every still-pending approval created by the replaced attempt; reviewers never approve stale output.
- Each project has configurable token and cost ceilings. Reaching either ceiling pauses new agent work and queues a request to raise the budget or end the run.
- Pending approvals have a configurable backlog threshold. Reaching it throttles new dependent work until approvals are resolved or expire.

## Architecture & Sub-Agents

- Mission profiles define goals, specialist roster, quality gates, allowed connectors, and delivery workflow.
- Planner creates dependency-aware task graphs.
- Research agents gather and cite external context through read-only connectors.
- Specialist agents perform architecture, design, implementation, review, security, documentation, DevOps, and monitoring work.
- A policy engine classifies all proposed tool actions before execution.
- An async approval queue stores human decisions and resumes dependent tasks after approval or rejection. It enforces expiry, stale-attempt cancellation, and backlog throttling.
- Runtime quality gates score agent output, retry weak outputs, and retain telemetry for evaluation.

## Data Sources & Auth

- SQLite remains the local development store; Docker/VPS volumes provide persistence.
- Connectors use project-scoped encrypted secrets.
- Operator API key protection is optional locally and required in a VPS deployment.
- Future team RBAC and managed cloud deployment are explicitly deferred.

## Non-Functional Requirements

- Restart-safe task recovery.
- Full audit trail for connector access, policy decisions, approvals, executions, retries, and failures. Audit payloads are schema-redacted: secret fields are stripped or masked while action targets, non-secret parameters, policy decision, and payload hash remain traceable.
- Budget and token tracking per agent and project, with enforced project ceilings that pause new work.
- Connector health checks, timeouts, rate-limit handling, and circuit breaking. The approval queue and policy engine also expose backlog/health thresholds that throttle new dependent work when degraded.
- No production deployment or external write without an approval record.

## Success Criteria

- A software-delivery project can use a mission profile to plan, research, and produce approval-gated artifacts end to end.
- The registry can register, disable, scope, and audit at least mock, web research, GitHub-read, and document-store connectors.
- Policy classification prevents external writes from executing without approval.
- Independent read-only tasks continue while an approval-gated action is queued.
- Every tool action has traceable connector, capability, risk class, outcome, and audit event.
